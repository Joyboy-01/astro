学校门口新开了一条小吃街，其中一家卖打抛饭的摊位，排了很多人。老板只有一套固定的炉灶和锅具：一个锅炒肉，另一个锅炒蛋。菜单有猪肉、鸡肉、牛肉三种选择。肉可以一次炒好几份，但一锅只能做一种。我们排的是一条按到场顺序排列的队，老板生产的却是一锅一锅、按肉类区分的饭。队伍里可能依次站着要猪肉、鸡肉、牛肉、鸡肉、猪肉的人。人和锅，遵循着两套不同的顺序。于是，先到的人不一定先吃上。刚来的人如果恰好点了正在做的肉，反而可能很快拿到。这是生产方式与排队方式不一致的问题。

这个摊位还有线上预订。提前点好口味，到店后不用排普通队，可以去另一侧等对应的那锅。听起来很好，于是我在周五的晚上预订了一份，打算大快朵颐。但预订并不意味着老板会提前做好一份，放在那里等你。于是六点的餐，我等到了六点四十。我点了猪肉，恰好在炒猪肉时到场，只要这一锅还能安排，就很顺利。但是我刚到，猪肉已经做完，后面又有很多人等鸡肉和牛肉，我还是可能要等另外两锅，甚至老板炒了两次鸡肉一次牛肉，于是我等了三个锅。

等待的时间我开始思考，有没有什么方式能够缩减等待时间。

最初，我很自然地想到了小程序：提前收集口味，安排批次，告诉大家几点来取。

但顾客预约的是一个时间，老板组织生产的单位却是一种肉的一锅。八点来的顾客，仍然可能分别要猪肉、鸡肉和牛肉。把他们都填进“八点”这个时间格子，并没有让一个肉锅获得同时炒三种肉的能力。而且，老板只有一个人。他一般在出摊前截止线上订单，拿着那份名单开始营业；忙起来以后，没有手机可用，也没有空不断确认谁到了、谁迟了、下一锅是不是该调整。如果提前做，就可能失去现炒的口感；如果等人到了再做，就仍然需要现场协调。线上点单记录了需求，却没有自动解决需求与生产之间的同步。

如果不约束条件，解决方法很容易变成“再加一个锅”“再雇一个人”或者“让老板实时看订单”。但这不是我想讨论的那个摊位了。我想保留四个条件：

- 炉灶、锅具和人手不增加。
- 临时经过的顾客也能买饭，不能要求所有人提前进群、预约或者学会规则。
- 老板营业时不用手机，也难以持续统计每个人的口味和等待时间。
- 饭要在顾客能够领取时现炒，不依赖提前做好、存放待取。

设备固定，并不意味着所有排锅方法的产出都相同。一锅只炒一份和一锅炒六份，效率可能不同。但任何优化都必须在现有设备内发生。

接下来的分析，先把炒肉锅视为主要瓶颈。炒蛋、装饭、打包同样需要时间；如果它们才是真正的瓶颈，就必须把它们也加进模型，不能把肉出锅直接当成饭已经交到手上。我让chatgpt帮我找一些合适的调度方法和解释，以下是一些记录

### 老板同样做了三锅，顾客的九分钟却不一样

为了把取舍看清楚，先构造一个简化例子。以下数字是说明原理的假设，不是这个摊位的实测数据。现在有十三个人已经到场：一个人要猪肉，六个人要鸡肉，六个人要牛肉。猪肉顾客最早来。假设每锅最多六份，不论做几份都用三分钟，没有额外装餐时间，也暂时没有新顾客。

老板可以先照顾最早到的人，也可以先做人数多的口味。

| 接下来怎么炒 | 猪肉顾客还要等 | 所有人从现在起平均多久拿到饭 | 全部完成 |
| --- | --- | --- | --- |
| 猪肉 → 鸡肉 → 牛肉 | 3分钟 | 约7.15分钟 | 9分钟 |
| 鸡肉 → 牛肉 → 猪肉 | 9分钟 | 约4.85分钟 | 9分钟 |

第一种安排的平均时间是 `(1×3 + 6×6 + 6×9) / 13`；第二种是 `(6×3 + 6×6 + 1×9) / 13`。两种安排都做三锅，都在九分钟结束，也都卖出十三份。区别在于，这九分钟如何分配给不同的人。先做鸡肉，可以让六个人在第三分钟就离开，平均等待更短。但最早到的猪肉顾客，会看着十二个人先吃上。这里没有一个脱离目标的“更优”。如果只看平均等待，第二种更好；如果强调先到者的保障，第一种更容易解释。而在真实队伍中，顾客还会持续到来。如果老板总是选择人数最多的口味，少数口味就可能一再被推后。

平均等待、最久等待、先到先得和每锅装满，并不是同一个指标。

### 让最早等待的人决定下一锅

计算机领域有一种很贴近的建模方式：把三种口味分别看成三个 FIFO 队列，锅是唯一的服务者。每次空闲时，决定访问哪个队列，并从中取出一批订单。一条直接的规则是：比较三个队首，谁最早到，下一锅就做谁的口味。

这条思路有正式研究。在 *Polling with batch service* 中，作者讨论了 **FCFS among queues**，也称为 **Israeli queue**：根据各队列中最早到达者决定下一次服务哪一类。[1]

针对炒锅容量有限、开炒后不再加人的情况，可以改造成下面的规则。这里是对文献思路的适配，不是照搬原论文的全部模型。

```text
顾客到场后，进入对应口味的 FIFO 队列。

每锅结束：
    找到三个非空队列中，到场最早的队首。
    下一锅选择他的口味。
    从该队列按先后取出至多 B 份。
    确定本锅名单，开始炒制。
    新来的顾客留在队列中，等待后续批次。
```

例如，队伍依次是：

| 到场顺序 | 口味 |
| --- | --- |
| 01 | 猪肉 |
| 02 | 鸡肉 |
| 03 | 牛肉 |
| 04 | 鸡肉 |
| 05 | 猪肉 |
| 06 | 鸡肉 |
| 07 | 牛肉 |
| 08 | 猪肉 |

假设一锅最多四份。第一锅由01号决定，做猪肉，带上05、08号。第二锅由尚未服务的02号决定，做鸡肉，带上04、06号。第三锅轮到03号，做牛肉，带上07号。08号仍然比03号先吃上。但03号不会因为后来又来了更多猪肉或鸡肉顾客，而永远失去机会：当他成为最早等待的人，下一锅就由他决定。

可以给这个性质一个很朴素的证明。假设你前面还有有限的 m 份待做订单，每锅都包含当前最早的一份，后来者不插到你前面，也不故意空等。那么至多再开 m+1 锅，就会有一锅包含你。这个界很保守，但说明后来者不能造成无限推迟。

它不保证平均等待最短，也不保证每锅装满。一个冷门口味只有一位老顾客时，老板可能需要为他开一小锅。另外，原论文包含无限批容量，以及特定到达、服务分布等假设。它的解析公式不能直接拿来估算这个摊位的等待时间。[1]

### 如果老板只想记住一个顺序

还有一个更省判断的办法：猪肉、鸡肉、牛肉轮着做，每种每轮最多一锅，没有人就跳过。它对应轮询系统中的有限服务思想。服务者访问多个队列，每次限制处理数量，避免一直停留在某一类。这里限制为“最多一锅”，是对批处理场景的具体设计。[2]

这个方法不需要比较谁等得最久。老板只需要知道轮到哪种、有没有人、这一锅做几份。但它保护的是口味获得服务的机会。假如二十个人等鸡肉，一个人等牛肉，平均轮换锅数，鸡肉顾客仍可能等很久。如果几天观察下来，鸡肉需求确实长期更多，可以在出摊前固定一个加权顺序，例如“鸡肉 → 猪肉 → 鸡肉 → 牛肉”。这样不用营业时实时计算，但比例选错仍然会带来积压。

“每种都轮得到”，也不等于“每个人一轮内都吃得到”。只要同口味前面超过一锅的人数，就得等待更多轮。

### 七点以后，还有人要上课

讨论到这里，还缺了一个很实际的条件：高峰期里，有些顾客之后要去上课。对他们来说，饭晚几分钟到手，可能就不值得继续等了。这时，订单除了到场时间和口味，还需要一个 **最晚取餐时间**。如果七点上课，走到教室要五分钟，那么最晚取餐可能是六点五十五；如果要先吃完，还要继续扣除吃饭时间。

用调度中的记号说，顾客 j 的截止时间是 `d_j`，实际完成时间是 `C_j`。`C_j > d_j`，就代表这份饭超过了他的可接受时间。一个自然的想法是借用 EDF／EDD 的思路：谁的截止时间最早，下一锅先做他的口味，再合入其他同口味订单。

但它仍然不一定能让最多人赶上课。再构造一个例子：一个人点猪肉，必须四分钟内拿到；六个人点鸡肉，必须五分钟内拿到。每锅三分钟，容量六份。先做猪肉，一个人按时，六个人超时。先做鸡肉，六个人按时，一个人超时。最早的截止时间，与最多的按时完成人数，又出现了冲突。所以目标还需要进一步说明：我们是想减少超时人数，减少总共迟了多少分钟，还是对一部分已经承诺的订单保证按时完成？这些问题对应不同的调度目标。

有一篇名称就很贴近的研究：*Minimizing number of tardy jobs on a batch processing machine with incompatible job families*。它考虑有限批容量、不同类别不能合批、每个任务有截止时间，并研究减少超时任务数量的方法。[3]

但文献中的给定订单集合，与现场不断到人的情形仍有区别。经典截止时间优先规则的结论，也不能越过合批、容量、不可中断等条件直接套用。如果两个人都只剩四分钟，却点了不同的肉，每锅要三分钟，那么无论如何排序，至少一个人来不及。算法需要识别这种情况，及时让顾客决定是否继续等，而不是把“优先处理”说成一定赶得上。

同时，没有明确截止时间的顾客也不能无限让位。照顾赶课者，需要和普通顾客的等待保障一起考虑。

### 软件里的三个队列，要怎么放到摊位前

到这里，写程序似乎已经不难。三个 `deque`，比较一下队首，取出同口味的若干订单。或者给每份订单加上截止时间，再用优先队列。真正困难的是：这些数据从哪里来？软件不会自动知道谁刚到、谁准备离开、谁虽然点牛肉但也接受鸡肉、谁必须十分钟后走。每一条信息，都需要某个人提供、更新和核对。这也是普通小程序在这里容易失效的地方。

对这个摊位，更值得先试的可能是一条总队伍，加一个很小的合批窗口：每锅结束，只问最前面还没拿到饭的人要什么肉，再从队伍前面固定一段里找同口味的人，按先后补进这一锅。没轮到的人保留原来的相对顺序，已安排的人移到取餐侧。

窗口有多大，需要试。只问前六人还是前十人，是合批机会与沟通成本之间的取舍，不能把某个数字当成通用答案。现场只需要说明一句话：

> 下一锅按队首口味做，同口味可以合锅；没轮到的保留原位。

如果老板连每锅询问都很难接受，就考虑固定轮换，用纸牌显示顺序。但纸牌同样需要有人更新，不能把它想成零成本的系统。至于赶课时间，也只能选择老板实际能接收的表达方式，比如纸质号码上写最晚取餐时间。只要无法可靠获取这项信息，就不能承诺算法会照顾到所有赶课的人。

预订单还需要一条明确规则：如果线上顾客可以不断插入现场队列，那么前面对普通顾客的等待保障就不再成立。预订究竟保证有料、保证某锅名额，还是只提供有限的优先权，都需要在执行前说明。

### 顾客之间还能做一点什么

并不是所有信息都只能交给老板。有些人只接受一种肉，有些人只是想吃一份饭。后一类顾客如果愿意，可以在下一锅尚有空位时，选择跟锅。这是一种自愿的需求调整：增加可用的合批机会，而不是让锅获得更多生产能力。前提是老板已经确认能加多少份，顾客不能自己认定有空位；换口味也不能挤掉已被安排的人。不愿意换的人，继续保留原位。

微信群则可以帮助熟客提前了解大概拥挤情况，选择错峰。但如果没有可靠的现场更新，它无法给出可信的实时等待时间，也不能替老板承诺某个批次。群外的人，更不应该因此失去正常排队的权利。

### 怎么知道这些想法到底有没有用

我并没有测量这个摊位的真实到达率、锅容量和每锅耗时，因此还不能断言哪种方案最好。如果一种算法在纸面上少等两分钟，却要求老板每锅多协调半分钟，真正的结果可能完全不同。

老板也有自己的目标。如果几种规则下每小时卖出的份数接近，没有明显的顾客流失，而新规则更费精力，他就缺乏改变习惯的理由。反过来，若能少重复解释、少争执、少漏单，它才可能同时改善顾客体验和老板的工作。

我最初以为，这条长队需要一个更聪明的小程序。后来发现，问题里最稀缺的资源，除了锅，还有老板的注意力。一套规则要走出代码，最终还得回答一个很具体的问题：当这一锅刚出、鸡蛋还要炒、下一位顾客已经开口时，老板能不能顺手把它执行下去？
